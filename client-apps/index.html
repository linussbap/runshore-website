1.1

Connect to the RunShore MySQL cluster

A port-forward makes the cluster reachable on 127.0.0.1:3307. MySQL Workbench confirms the connection.

1.2

Create the WordPress database and user

A dedicated database and user for WordPress. Use your own strong password; never one from a document.

CREATE DATABASE wordpress_demo
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;

CREATE USER 'wordpress_demo'@'%'
  IDENTIFIED BY 'REPLACE_WITH_YOUR_OWN_STRONG_PASSWORD';

GRANT ALL PRIVILEGES ON wordpress_demo.* TO 'wordpress_demo'@'%';
1.3

Start WordPress

WordPress runs on PHP's built-in server at 127.0.0.1:8088, alongside the MySQL port-forward on 3307.

1.4

WordPress is running on RunShore's MySQL

1.5

Generate load

tools/client-apps/wordpress/workload.sh start

The workload writes realistic content through WordPress itself: order posts in a RunShore Workload category.

1.6

Observe in PMM

Baseline: about 22 operations/s at 0.3 ms latency, no errors, 9 connections.

Additional load: throughput and latency rise; CPU and memory follow.

A real application-to-database connection, using RunShore's deployed MySQL infrastructure.

2.4

Smoke test of the load generator

node tools/maintenance/idurar_crm_erp_load.js --execute --smoke-test
  • One business bundle: a customer, a quote, an invoice and a payment, created through IDURAR's own API, then deleted: 4 inserts + 4 deletes.
  • Only tagged RunShore test records (RSLOAD-IDURAR-*) are touched; earlier test records are purged first, so every run starts clean.

  • Result: authentication PASS, bundle created 1/1 (100%) in 0.2 seconds.

What this shows

  • RunShore's databases serve real applications, not only synthetic benchmarks.
  • Every database is paired with an observability tool, and the application's own traffic is visible there.
  • Loads are tagged, staged and cleaned up, so every run starts from a clean environment.
  • Recovery tests (PITR, failover, replication) run while applications are connected.
